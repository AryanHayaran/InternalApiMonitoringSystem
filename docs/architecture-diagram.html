Internal API Monitoring System

Monitoring System Architecture

How a health check becomes an incident. One producer, one topic, two partitions, two independent consumer groups — and the ordering rules that keep the verdicts correct.

01The three ordering rules

Database write comes first

A failed publish delays detection by one cycle; a wrong order produces a wrong verdict. The next cycle's event sees the orphaned row, so the system self-heals within 60 seconds.

Both groups read everything

Separate offsets, separate lag. The rollup can fall hours behind or crash entirely and incident detection is untouched. That isolation is the whole reason it is a second consumer group rather than a second function call.

The key pins the ordering

Keying by endpoint_id sends every check for an endpoint to the same partition — and therefore the same consumer. Without it, two detectors could race on the same three-check window.

04Failure behaviour

Endpoint is slow or down

Isolated per endpoint by its own error boundary, a 20 s deadline, and gather(return_exceptions=True). The cycle finishes for everyone else.

Kafka is unavailable

Checks are still recorded in PostgreSQL. The producer reconnects behind a lock, so 25 concurrent checks cannot storm a dead broker.

A message is malformed

Decoded in our own code rather than inside the driver, so it can be logged, committed past, and skipped — instead of being re-read forever.

Redis is down

Every call fails open. Rate limiting allows, revocation checks pass, and the API keeps serving. Verified by stopping the container.
